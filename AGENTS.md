# Mandatory 3D quality skill

The root agent and every delegated agent doing 3D modeling, scenes, materials,
lighting, camera presentation, rigging, animation or optimization must read and
follow [high-fidelity-3d](/Users/williamguinaudie/.codex/skills/high-fidelity-3d/SKILL.md)
before starting that work. Include this skill path in every 3D delegation.
Build a detailed, convincing high-quality source and review its anatomy,
silhouette, materials and motion before optimizing for runtime. The root agent
must inspect the visual evidence; passing tests alone does not establish quality.

# Task size scale

Classify every request before starting and scale the verification to it. When
unsure, pick the smaller size; the user can ask for more.

- **Small**: a rule, text, scoring, value, copy or styling tweak in known
  files. Implement, run the relevant unit tests and stop. No browser QA pass,
  no screenshots, no viewport matrix, no preview server just to confirm. The
  browser may still be used while developing if it is genuinely needed to
  find or understand something.
- **Medium**: a new feature, a changed interaction or a layout change in one
  game. Tests plus one focused browser check of the changed view.
- **Large**: a new game, world, artwork integration, shared navigation or
  cross-game change. Full verification as the sections below require.

The browser/touch/viewport checks required elsewhere in this file apply to
medium and large tasks. For small tasks, say plainly that browser QA was
skipped by size rather than implying it was done.

# Render resolution follows the screen and the device

Every game canvas, WebGL or 2D, sizes its drawing buffer through
`components/game/render-quality.ts`; never write `Math.min(devicePixelRatio, 2)`
or a fixed pixel budget again. The aim is the screen's native density (a 4K
monitor gets all of its pixels, a 3× phone its full 3×). `devicePower()` sorts
the device into high, mid or low from its graphics chip, cores and memory
(`?power=low` on any page tries a class). Animated scenes start at
`startLevel()` on the shared frame pacer (`components/game/render-pacer.ts`),
which climbs to native when frames have room and steps down when they slip.
Light scenes use `startRatio()` and still drawings `stillRatio()`, both
recomputed on resize. A game keeps its own floor (`floorAt`), so no device
draws below what it drew before. Rota keeps its tiers with a native step on
top (`lib/games/rota/quality.ts`).

# Docker image and release build time

The release image is built for linux/amd64 and linux/arm64 on GitHub's amd64
runners, so every arm64 step runs under QEMU, roughly ten times slower. Slow
releases have happened several times; keep the image job to a few minutes.

- Any stage that installs dependencies or builds (`npm ci`, `vinext build`,
  asset checks) must start `FROM --platform=$BUILDPLATFORM`, so it runs once,
  natively, and every target platform copies its output. The per-platform
  runtime stage may only COPY files and run trivial commands; never add
  `npm install`, a build, or native addons there. If a native dependency is
  ever unavoidable, use a native arm64 runner rather than QEMU.
- Keep the Docker context small: `.dockerignore` carries the production asset
  allowlist generated by `npm run check:assets`; never send source art,
  `node_modules` or other large files into the context.
- After every release, compare the Release run with the previous one
  (`gh run list --workflow Release --limit 3`). If the image job takes more
  than about twice as long, read the step timings
  (`gh run view <id> --log | grep -E 'DONE [0-9]+'`) and fix the cause before
  shipping the next release. Changes to the Dockerfile or the release workflow
  are checked locally with a multi-platform buildx build and
  `node scripts/container-smoke.mjs`.

# Global game navigation and viewport contract

Applies to every game, every game family, solo and online, practice and live play:

- Top left contains only the back/return control and game name. For the table admin alone it holds only the Table button instead (`TableManager`, `components/game/table-manager.tsx`), in the back control's slot; the back control and name are hidden for the admin. It drops the table panel along the left side: the players (Make admin, a bot for an away seat), then Leave (the back control's own action), Back to lobby and Close table, the two ending actions asked once in place. Table settings never sit in the Menu, and nobody else sees them. Menu, Others, time/advance-time and fullscreen controls belong at the top right; on wide screens Others sits directly below Menu. On phones (≤600 px) every game uses one top bar, modelled on Mora: back on the left, the round pill in the centre, Others then Menu on the right, and the player badges in a row beneath (full names while they fit without sideways scrolling, the contracted badge otherwise, via `useBadgeFit`). Nox keeps its badges on the table seats. Arena is the exception by decision: its top bar holds only a back button (left) and the clock with the crown counts and a small pause button (right) that opens the shared menu; no name, badges or Menu label (see its DESIGN.md section). Nothing on the bar may clip a badge's corner marks (the placement die). The contract lives in `components/game/mobile-hud.css`; no game-specific reversal. Only show Others where there is something private to see (not Know Me or Quiz).
- Phones are portrait only and play full screen where the browser allows it: `components/game/mobile-viewport.tsx` asks for fullscreen and a portrait lock on a tap while a game is open (or on a `data-starts-game` button), respects leaving fullscreen from the menu, and shows a rotate screen on landscape phones. Short landscape phone layouts are no longer a target. Diner is the exception by decision (9 October 2026): it plays sideways on phones (stick left, buttons right), wraps its screens in `DinerLandscape` (`components/game/diner/diner-landscape.tsx`), locks landscape and shows a rotate screen on upright phones; see its DESIGN.md section.
- Undo always has its own visible slot in the dock row directly above the hand; no menu, plate, extension or confirmation may cover it.
- Treat the playing screen as one viewport. Strongly avoid whole-page scrolling to reach the board, choices, hand, confirmation or navigation. Reflow into columns or side rails, reduce decorative spacing and duplicate headings, and fit the active board before reducing readable text or touch targets. Never hide essential controls with overflow clipping to claim a fit.
- Keep long rules, history, comparisons and optional inspections in explicit overlays with internal scrolling and restored focus. Extreme zoom/accessibility fallbacks may scroll locally; report them honestly rather than calling them viewport acceptance.
- Preserve in-progress choices when switching between options. Refreshing options within an active view must keep that view open.
- Read [game-world-layout](.agents/skills/game-world-layout/SKILL.md) for any new game or navigation/responsive layout change, including games without illustrated boards. Reuse `GameNavigation` for party/world screens and the shared trio toolbar for Nox/Mora/Yata. Verify portrait, short landscape, tablet, desktop, long labels and maximum player counts; report browser/touch checks separately.

# Pacing: players lock choices, the host moves on

Applies to every game, solo and online. Wait for players only when they lock in
their own decision (a ranking, guess, pin, card or final submit). Never make
every player confirm moving on to the next step, reveal or round. That single
**Next** belongs to the table host, and the game waits for the host even when
everyone has locked in. The table admin hosts the table (sets up, starts and
closes it): the creator, until they hand it over (Make admin), leave the lobby
or stay away for thirty seconds; then the earliest joiner still here takes it
for good, in every game, and a Folio run the table moved on to follows. In the
lobby the admin may pick another player to lead the next match only: that
player presses Next during that one match, and the lead returns to the admin
when it ends. While the leader is disconnected any
seated player may press Next. Bots never move the table on. See the
23 September 2026 section of [docs/DESIGN.md](docs/DESIGN.md).
In Folio the host alone plays the shared board. Everyone else plays on their
own board, and each move they enter becomes a suggestion the whole crew sees
under the board; the host plays it (tick) or turns it down (cross). See the
26 September 2026 table admin section of the same file.
Party games end each round, and each match, with the host's pick of what
comes next (another round, another game of the set, or finish; which party
game next). Setup's Next round choice can hand it to a ten-second table vote
instead; it is off by default. A vote never waits on anyone: most votes wins
and silence doesn't count. See the 29 September 2026 section and the table-votes
section of the same file.

# Game menus, saving and copy protection

- Every game's menu is the shared `GameMenu` (`components/game/game-menu.tsx`): a panel that drops down from the Menu button at the top right, along the side of the screen, never a modal over the table. Its order is fixed: Resume (only where the game pauses, Arena), How to play, the game's own entries, sound switches inline (never a separate sound window), Fullscreen where the browser supports it, extra content (stats), then Leave. Table settings are the Table button's, never the menu's. Games tint it with a `theme`; they do not build their own menu. `GameNavigation` renders it from its `menu` prop.
- Every setup modal has one fixed height (Nox's: two decks beside three extensions). Boards and other picture choices show two at a time and extensions three, behind the row's pager; rows that still do not fit page with `SetupOptions` (`components/game/setup-pages.tsx`). Never let a setup grow or scroll to fit; see the 1 October 2026 setup section of [docs/DESIGN.md](docs/DESIGN.md).
- There is no Confirm moves setting and no Advanced view: a tapped or dropped card plays at once. Only Nox passing keeps its lock plate beside the hand. Do not bring either setting back.
- Leaving a game that keeps your progress (saved board-game matches, online matches, Folio runs) opens the shared `LeaveDialog` (`components/game/leave-dialog.tsx`, with `useLeaveDialog`): a check mark, the question, one line saying the game is already saved, then **Leave** above **Keep playing**. The buttons never swap, solo or online; rarer actions such as the host's End for everyone go beneath them. Leave waits for anything still in flight. There is no saving animation. Lucky leaves directly once its scratches have landed.
- Nothing on the site can be selected or copied, on any device (`app/globals.css` and `components/game/copy-guard.tsx`): no text selection, copy shortcut, long-press callout, context menu or image drag. Fields you type into are the only exception. Share links through copy buttons (`navigator.clipboard`).

# Rules and explanation UI

Required for every How to play, rule inspection and extension explanation, in every game:

- Arena's How to play (`components/game/arena/arena-rules.tsx`) is the model for wording and presentation. Build rules only from `Rules`, `RuleSection` and `RuleList` in `components/game/rules.tsx`: a few short sections, each a two-to-four word heading and one or two short paragraphs with the key words in bold; limits and exceptions in the section's single purple note; reference lists (cards, dishes, habitats, books, puzzles) as a compact `RuleList`. Goal first, then what you do, scoring, how it ends.
- Write plainly: short everyday words, second person, present tense, no filler, each thing said once, only the one gesture a player needs; keyboard shortcuts go in a note. Every number must match the engine.
- Games tint rules only through the `--rules-*` tokens (`app/globals.css`); do not introduce per-game text sizes, alternate callouts or unstructured rule blocks.
- Reuse the same rule components in setup, match help, and inspections. Make changes to the shared component/styles when the visual standard changes.
- Setup extension explanations use a separate, larger modal above setup, opened by long-press, keyboard inspection, or Rules. Keep setup selections intact, restore focus on close, and constrain the modal to the viewport with internal vertical scrolling.
- Keep extension controls compact and graphical; on-board overlays must not cover placement slots or add board height. Content sets and extensions are independent, so rules and art must resolve through the current content set.
- Check overview and individual inspections, narrow-screen readability, and keyboard/long-press access when changing this UI. Report separately whether browser and touch behavior were actually checked.

# Gamehub creative direction

- Read [docs/DESIGN.md](docs/DESIGN.md) before visual, interaction, naming or extension work. Current implemented names are Blackwake, Elsewild and Nightshift; new names are under exploration and internal IDs remain stable.
- Required naming rule: game names must be short, simple to read aloud, and reasonably easy to pronounce for non-English speakers across languages. Prefer clear syllables; avoid English-dependent puns, opaque compounds and difficult consonant clusters. Treat proposed names as provisional until chosen; do not rename running games during concept-only work.
- Abstract strategy games (Nox, Mora, Yata) take short abstract names. Party and less abstract games (Know Me, Quiz) take plain, literal names that say what the game is; never an invented word.
- The previous names, themes and artwork are not design constraints. Invent names and imagery consistent with the documented worlds; preserve gameplay and scoring identity unless a rule change is requested.
- Give every game a strongly distinct visual identity, including materials, typography, palette, illustration and presentation; palette swaps of one shared skin are insufficient. Keep Nox’s approved flat treasure-map poster direction (the Chart, 26 September 2026). The library is a warm, neutral home for these distinct worlds. Review generated images and delegate image generation. Each Elsewild environment has its own geography and slot coordinates; match environment scale to readable creatures.
- Each extension adds one mechanic and is independently selectable. Setup has one Extensions heading, compact graphic tiles, and an information control on each tile. Rules use the shared modal and the shared rules pieces (`components/game/rules.tsx`).
- Put turn/waiting states beside the top players, confirmations beside the hand, and prominent graphical actions near the hand. Never restore the bottom status strip.
- Respect reduced motion and mute. Validate hidden simultaneous decisions and atomic moves in solo and online play; report browser/touch checks separately.
- **Hard rule: no noise text in the playing layout, in every game.** No eyebrows, subtitles, taglines, duplicate game titles, or helper and status sentences. The board, buttons, avatars, dots and images carry the state. Keep only content (prompts, clues, answer labels), names, scores and one short word per action; explanations go in Rules. When in doubt, cut the text.
- **Hard rule: never ship a flat, uninspired screen.** Give every game depth and energy (a considered palette, light, glow or material, and a centrepiece worth looking at) while staying sleek rather than busy. Wrap prompts with `text-wrap: balance` so lines never break awkwardly.
- Know Me (`orin`, formerly Tribu) holds Top Five, Dial and Ten Coins as one game with an opening pick and an again/switch/end pick each round; see the Tribu and 29 September 2026 sections of [docs/DESIGN.md](docs/DESIGN.md). Every Know Me game runs the same way: everyone answers for themselves at once, then everyone guesses every other player at once (one tab per player, one lock), then the answers are revealed one player after another. Always everyone for themselves: no teams. Only Top Five prompts carry a flag, on each option.
- Impostor (`impostor`) is a drawing party game for 3–8 humans: everyone draws the same secret word except the impostor, who unknowingly has a close neighbour, then writes one word, then accuses. Nobody is told who the impostor is. It keeps its look (an evidence wall at night) and stays human-only online; see the Impostor section of [docs/DESIGN.md](docs/DESIGN.md).
- Puzzles (`folio`, formerly Folio, renamed 9 October 2026) is the co-op run of famous daily puzzles; its id, route (`/folio`), code names and saves stay `folio`, and every public text says Puzzles.
- Lucky (`relic`, formerly Relic) is a shared scratch-ticket room: every book is a small puzzle with three levels, every ticket is bought (half of what a careful player wins) and held one at a time, it pays the moment it is over, and upgrades are a forty-node tree of big steps. See [docs/relic.md](docs/relic.md) and the Lucky section of [docs/DESIGN.md](docs/DESIGN.md).
- Quiz (`miro`, formerly Sabi and Mundo) holds short trivia games the same way, Atlas, Sizes, Years and Order today, always everyone for themselves; see the Sabi section of [docs/DESIGN.md](docs/DESIGN.md). Every Quiz game uses the shared measuring-desk pieces in `components/game/sabi.css` and `sabi-steps.tsx`, and scores up to 100 per prompt. The Know Me and Quiz sets share `lib/games/party/tribu.ts` (the switch) and `components/game/reveal-motion.tsx` (quick reveal motion: count-ups and staggered drops and pops, under two seconds, off under reduced motion). New reveal and results screens use that kit. A reveal's Next names what it opens: the next player, place, event or set, or the end of the round (`NextStep` in `components/game/know-me-parts.tsx`).

# Illustrated board workflow

Before creating or changing a game's illustrated board, responsive scene framing or hand presentation, read [game-world-layout](.agents/skills/game-world-layout/SKILL.md). Use its shared source/crop geometry, landscape and portrait planning, and generation brief. Keep the scene viewport independent of extensions, confirmations and hand count. Hands occupy a rounded floating tray above the bottom safe area that never zooms the world. Mora and Yata keep a fixed-size tray. Nox is the exception by decision: its plank shelf shrink-wraps the cards in hand (`--hand-step` from the card count in `table-worlds.css`), the die column stands exactly as tall as the shelf, and the confirm plate sits level beside it with Clear always present. Every die uses the shared cube in `components/game/die.css`; games set only `--die-size` and the face colours, never their own cube geometry. Apply this workflow to future games while preserving each game's distinct art direction.

- In an open illustrated game, float navigation/menu controls rather than reserving a top bar. Scale the fixed hand dock down on tablets and phones. On phones the dock (abilities, confirm plate, Undo) is one row resting directly on the hand, whatever its height, and the stage takes the rest. Fullscreen and orientation requests must be user-triggered and feature-detected; never block portrait play on unsupported devices.

- Illustrated-board generation must protect complete landmark silhouettes (roofs, lookout huts, flags, canopies and bases), not only placement slots. Derive their safe source region from current device cameras and offsets before prompting; only expendable scenery may extend outside it. Keep the approved source/crop footprint during artwork refreshes. See the game-world-layout skill for measurement and acceptance checks.

- Before regenerating illustrated boards for zoom/framing feedback, compare source/crop ratios, complete-landmark bounding-box ratios, native slot size and per-device sampling density. Specify a measured intermediate composition; do not turn a small crop miss into a large global zoom-out. Use device-specific landmark fitting when appropriate, with both edge-coverage and landmark checks.

- Illustrated-board framing must be checked after browser zoom crosses responsive breakpoints. Derive minimum source-cover scale and maximum full-landmark fit from actual available dimensions, permitting modest closer framing where spare room exists. Test iPad-size and fractional browser-zoom viewports; do not regenerate artwork to conceal a camera-sizing bug.
- For any full-bleed illustrated board, follow [docs/illustrated-worlds.md](docs/illustrated-worlds.md): it names the data contract, runtime pieces, tooling and the two artwork skills.

- Shared game navigation: on wide screens Others sits directly beneath Menu and the player badges share the top navigation baseline; on phones see the top-bar contract above. Remove redundant Table and passing-direction controls; passing order remains available inside Others. Accepted artwork is fixed; do not leave A/B review selectors in playing scenes.


# Library cover artwork

- The landing page shows real gameplay footage of every game, filmed wide
  and tall with the interface hidden (see the 8 October 2026 library section
  of [docs/DESIGN.md](docs/DESIGN.md)); re-film a game with
  `node scripts/reels/record.mjs <id>` when its look changes. The square
  cover is each card's face and stands in for a game without footage.
- Use dedicated full-bleed square illustrations, equally sized across the library.
- The setup lid uses each game's separate wide cover, cut to 3:1 (`wideCover`
  in `lib/games/box-covers.ts`); keep its title and subjects inside the middle
  30–70% of the generated height so short screens can trim the band.
- Generate the exact current game title inside the image, with legible custom
  typography integrated into the composition. Never overlay visible DOM titles
  or add duplicate titles to cover art. Keep accessible control and dialog names.
- Regenerate from written game/theme/style briefs without previous images as
  references unless the user explicitly requests a reference-based edit.
- Represent the game's world and meaningful elements in its own visual style;
  never use a gameplay screenshot, interface replica, box mockup or gray mat.
- Review title spelling, thumbnail legibility, edge coverage and square framing
  before integration. Preserve sources, versioned outputs and exact prompts.
- `lib/games/box-covers.ts` is the shared library/online cover source. Update the
  game registry, covers and public UI together when changing public names; keep
  stable internal IDs and saves intact.

## Shared game progress

Games with a fixed number of rounds (Nox, Mora, Yata, Folio, Rota) show the round as a pill centred at the top of the screen, on its own plate so it reads over the artwork: `<GameProgress round>` from `components/game/game-progress.tsx` (or `round` on `GameNavigation`). On wide screens it hangs just beneath the centred player badges; on phones it sits in the centre of the top bar. Folio is the exception by decision (26 September 2026): on every screen its pill sits in the centre of the top bar with the crew and hearts beneath it, the phone layout. Games whose length changes as they go (Know Me, Quiz) show no round count. Other progress (Lucky's tally) stays small beneath the back control. Never put progress in a bottom action panel. Atlas does not show a medium/hard badge. Know Me and Quiz (every game inside them) require human players in every seat; no solo bot matches, bot-filled online seats, or bot replacements.
